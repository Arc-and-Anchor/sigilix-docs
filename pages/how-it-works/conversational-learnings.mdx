# Conversational Learnings

A reviewer who keeps flagging the same non-issue is a reviewer your team learns to ignore. The fix is not a config file nobody updates; it is the ability to tell the reviewer, in the moment, what your codebase actually does — and have it remember.

Sigilix learns from conversation — wherever you talk to it. When a finding is wrong for a reason specific to your repo, you reply in plain language. Sigilix records the rule, applies it judiciously in future reviews, and — crucially — tells you when a later review was shaped by something it learned. And it is not only pull requests: correct the assistant in Slack, or fix one of its calls on a Linear issue, and that lesson lands in the same memory. Learnings are scoped to your repository or your organization and stay with your team — what one customer teaches is never shared with another.

## Teach a rule in three ways

<Steps>

### Reply to a finding

The most natural path. A finding fires, you disagree, and you say why: <em>"we use integer cents here, this isn't a float-rounding bug."</em> Sigilix turns that reply into a rule scoped to this repo.

### @sigilix remember …

State a rule directly, without waiting for a finding to react to:
<br />
<code>@sigilix remember we use integer cents for all money values</code>

### @sigilix forget …

Retire a rule that no longer applies:
<br />
<code>@sigilix forget the integer-cents rule</code>

</Steps>

<Callout type="info">
When Sigilix captures a new rule, it confirms with a <strong>"Learned something new"</strong> footer on its reply, so you know the lesson landed and did not vanish into the thread.
</Callout>

## One memory, every surface

You do not only teach Sigilix in a pull request. Wherever you work with it, the same memory is listening — and every surface both **contributes to** and **draws from** it.

<FeatureCards>
<FeatureCard title="In code review">
    Reply to a finding, use <code>@sigilix remember</code> / <code>@sigilix forget</code>, or just ask <code>@sigilix</code> a question on the PR. These lessons are scoped to the repository.
</FeatureCard>
<FeatureCard title="In Slack">
    Teach or correct the Sigilix assistant in a thread — <em>"we deploy on Fridays, don't flag that"</em> — and the rule is captured at the organization level.
</FeatureCard>
<FeatureCard title="On Linear">
    Correct one of Sigilix's triage calls on an issue, and that lesson is recorded for the organization too.
</FeatureCard>
</FeatureCards>

Because it is one shared memory, a rule you teach in Slack can shape a later code review, and a correction on a PR can inform how the CLI agent works. Repository lessons stay with the repo; organization lessons apply across everything your org connects.

Not every message becomes a rule. A quality gate — an extractor backed by deterministic filters — keeps only durable, generalizable instructions. Questions, acknowledgements, status updates, and one-off chatter are ignored, so the memory stays a set of real conventions rather than a transcript of everything anyone ever said.

## Applied judiciously, and attributed inline

A learned rule is not a hard mute. Sigilix reasons about whether the rule applies to the specific code in front of it, rather than blanket-suppressing a whole category. When a later review is shaped by a learning, the finding (or its absence) is attributed inline — you will see a note that it was **applied because of a learned rule**. The attribution matters: it keeps the system honest and lets you see exactly which lesson changed the outcome.

<FeatureCards>
<FeatureCard title="Judicious application">
    A rule narrows judgment where it is relevant; it does not silence an entire severity or category. Safety-critical and security findings remain protected.
</FeatureCard>
<FeatureCard title="Inline attribution">
    When a learning changes a review, Sigilix says so on the spot — "applied because of a learned rule" — so the influence of memory is visible, not hidden.
</FeatureCard>
</FeatureCards>

## Where Learnings sit in the pipeline

Conversational Learnings is the memory gate of the [believability pipeline](/how-it-works/believability-pipeline). After a candidate finding has cleared evidence, provenance, refutation, and received its proof-tier receipt, it is weighed against what Sigilix has learned about this repo. A finding that contradicts a learned rule can be down-weighted or suppressed before it ever reaches the PR.

Learnings is also a layer of [earned context](/how-it-works/earned-context): every rule you teach becomes reusable understanding that later reviews — and the CLI, the Slack assistant, Linear triage, and Deep-Research Chat — can draw on.

<Callout type="info">
Learnings is the headline mechanism of review memory. A secondary, statistical signal also exists — Sigilix tracks accept-and-dismiss patterns across findings — but the plain-language rules you teach are the primary, explicit way to shape how Sigilix reviews your code.
</Callout>
